# Правила разработки интеграций, зависящих от ESP32 Manager

**Статус:** обязательный стандарт для новых специализированных Home Assistant интеграций экосистемы ESP32.

## 1. Базовый принцип

ESP32 Manager (домен esp32_ota) — обязательная базовая интеграция и единственный владелец общей идентичности физических ESP32 в Home Assistant. Специализированная интеграция реализует конкретный продукт: датчики, ворота, освещение и т. п. Она расширяет общую запись ESP32 собственными сущностями и данными, но не подменяет Manager и не дублирует его функции.

Поток зависимостей:

    ESP32 firmware / ESP32 Platform Core
                     |
                     v
              ESP32 Manager
                     |
             public API + HA events
                     |
                     v
        Specialized integrations
                     |
                     v
           Product entities / UI

Специализированные интеграции не должны зависеть друг от друга. Общие функции и сведения проходят через ESP32 Manager.

## 2. Обязательная зависимость

В manifest.json каждой специализированной интеграции обязательно указывается:

    {
      "dependencies": ["esp32_ota", "mqtt"]
    }

Другие зависимости добавляются только при фактической необходимости. Если интеграция не использует MQTT напрямую, не следует объявлять mqtt без причины.

Перед использованием API интеграция обязана проверить его наличие и версию. Если Manager не настроен или версия API не поддерживается, setup должен завершиться через ConfigEntryNotReady с понятным сообщением. Нельзя молча запускаться в урезанном режиме или пытаться самостоятельно обнаруживать ESP32.

## 3. Публичный API Manager v1

API публикуется после успешного setup config entry Manager:

    manager_api = hass.data.get("esp32_ota", {}).get("api")
    if not isinstance(manager_api, dict) or manager_api.get("version") != 1:
        raise ConfigEntryNotReady("ESP32 Manager API v1 is unavailable")

Поддерживаемые методы:

| Метод | Контракт |
|---|---|
| get_device(device_id) | Snapshot одной известной идентифицированной ESP32 или None |
| get_devices() | Tuple snapshots всех идентифицированных ESP32 |
| register_remove_handler(domain, async_handler) | Регистрация async-обработчика каскадной очистки; возвращает unsubscribe-функцию |

Snapshot — detached-копия, а не ссылка на внутренний runtime-объект Manager. Текущие поля:

| Поле | Значение |
|---|---|
| device_id | Стабильный 12-значный uppercase hardware ID |
| name | Исходное имя из MQTT identity |
| name_by_user | Пользовательское имя из HA Device Registry или None |
| manufacturer, model, sw_version | Общие метаданные физического устройства |
| available | Текущее значение availability |
| availability_received | Получено ли актуальное сообщение availability |
| identity_received | Для опубликованного snapshot всегда true |
| profile | Профиль прошивки или None |
| product_id | Идентификатор продукта или None |
| capabilities | Список возможностей профиля |
| operations | Словарь операций профиля; это метаданные, а не API выполнения команд |

Не изменяйте snapshot и не сохраняйте его как собственный источник истины. Если нужны дополнительные сведения, интеграция хранит только свои доменные данные.

Пример чтения:

    snapshot = manager_api["get_device"](device_id)
    if snapshot is None:
        return
    is_available = snapshot["available"]
    profile = snapshot["profile"]

## 4. События жизненного цикла

Manager публикует события Home Assistant:

| Событие | Данные события | Действие потребителя |
|---|---|---|
| esp32_ota_device_added | device: snapshot | Добавить/синхронизировать устройство |
| esp32_ota_device_updated | device: snapshot | Обновить доменную проекцию и доступность |
| esp32_ota_device_removing | device_id | При необходимости остановить текущие операции |
| esp32_ota_device_removed | device_id | Удалить остаточное runtime-состояние |

Правильная последовательность запуска:
1. Получить get_devices() и синхронизировать начальное состояние.
2. Подписаться на события добавления, обновления и удаления.
3. Для каждого события использовать стабильный device_id.
4. Делать обработчики идемпотентными: повторный snapshot/event не должен создавать дубликаты.

Не полагайтесь только на события: интеграция могла быть перезапущена позже Manager или пропустить событие во время выгрузки.

Пример подписок:

    unsubscribers = [
        hass.bus.async_listen("esp32_ota_device_added", handle_device_event),
        hass.bus.async_listen("esp32_ota_device_updated", handle_device_event),
        hass.bus.async_listen("esp32_ota_device_removed", handle_device_removed),
    ]

Все функции unsubscribe сохраняются в DATA_UNSUB и вызываются при успешной выгрузке config entry.

## 5. Общая запись Home Assistant Device Registry

Идентификатор физического ESP32 всегда общий:

    identifiers = {("esp32", device_id)}

Но специализированная интеграция не должна создавать или обновлять запись шлюза самостоятельно. Этим занимается ESP32 Manager.

Правила:
- Не используйте домен специализированной интеграции как namespace шлюза.
- Не создавайте второе HA-устройство для той же ESP32.
- Не дублируйте имя шлюза, manufacturer, model, sw_version, профиль и availability в собственном реестре.
- Не перезаписывайте name_by_user; пользовательское имя принадлежит Home Assistant Device Registry.
- Дочерние устройства продукта связывайте с ESP32 через via_device=("esp32", device_id).
- Идентификаторы собственных датчиков/исполнительных устройств должны быть стабильными и независимыми от отображаемого имени или Area.
- Комнаты/Areas назначаются штатными средствами Home Assistant.

## 6. Границы MQTT-подписок

ESP32 Manager — единственный владелец общих MQTT-подписок:
- esp32/+/device/info — identity;
- esp32/+/device/profile — product profile;
- esp32/+/availability — online/offline;
- общие системные статусы Manager.

Специализированной интеграции запрещено самостоятельно подписываться на эти топики, разбирать общие payload или создавать на их основе свой реестр шлюзов.

Разрешено подписываться только на продуктовые топики: телеметрия, product registry, product commands/results и т. п.

Требования к продуктовым MQTT-топикам:
- Документировать все топики, payload, QoS и retain.
- Использовать стабильный device_id из Manager для привязки сообщений к шлюзу.
- Проверять, что шлюз известен Manager, прежде чем принимать его продуктовые сообщения.
- Валидировать JSON, типы, диапазоны, версии протокола и идентификаторы.
- Не считать retained измерение доказательством текущей доступности датчика.
- Команды публиковать с retain=false; retained использовать только для восстанавливаемого состояния.
- Для команд с ответом использовать correlation ID, проверять соответствие ответа запросу и ограничивать время ожидания.
- Не помещать секреты в retained payload, логи, HA state, события, diagnostics или persistent storage.

## 7. Product profile и доступность

Общие поля profile, product_id, capabilities, available и sw_version читаются из snapshot Manager.

Интеграция самостоятельно проверяет соответствие текущего профиля своему продукту: ожидаемые schema_version, product_id, версия прошивки и обязательные capabilities.

Если профиль отсутствует, очищен перед OTA или не соответствует продукту:
- не создавайте новые продуктовые сущности только на основании старых retained данных;
- переводите зависимые от профиля сущности в unavailable;
- не удаляйте устройства/сущности только из-за временного отсутствия профиля;
- при получении подходящего профиля восстанавливайте состояние идемпотентно.

Доступность физического шлюза берётся из Manager. Доступность дочернего датчика может дополнительно зависеть от собственной телеметрии и таймаута, но не должна подменять availability ESP32.

## 8. Хранение данных и сущности

Интеграция хранит только собственную предметную область: продуктовые идентификаторы и привязки, пользовательские настройки продукта, собственные retained snapshots/measurements, pending-команды, correlation IDs, результаты и tombstones для защиты от восстановления устаревших retained данных.

Запрещено дублировать в persistent storage общие метаданные ESP32, доступные через Manager.

Persistent данные должны иметь понятную схему и версию. Миграция должна безопасно обрабатывать отсутствующие и невалидные данные. Секреты не должны попадать в обычное хранилище без отдельного согласованного механизма.

Entity и Device Registry:
- Уникальные unique_id строятся из стабильного идентификатора продукта и физического идентификатора дочернего устройства.
- Entity platform корректно восстанавливает сущности после перезапуска.
- Удаление продукта из собственного registry удаляет его entities и child devices.
- Временная недоступность не является основанием для удаления сущности.
- Имена сущностей и устройств не должны использовать MAC как единственный пользовательский label, если доступны имя и Area.

## 9. Каскадное удаление — обязательная реализация

Каждая специализированная интеграция обязана регистрировать cleanup handler через API Manager:

    async def async_remove_gateway_data(device_id: str) -> None:
        # Idempotently remove all data owned by this integration for device_id.
        ...

    unsubscribe_remove_handler = manager_api["register_remove_handler"](
        DOMAIN,
        async_remove_gateway_data,
    )

Handler должен быть асинхронным, завершать очистку до возврата и быть безопасным при повторном вызове.

Он обязан удалить только данные указанного device_id:
- дочерние HA devices и их entities;
- продуктовые runtime-кэши;
- persistent storage, registry и пользовательские привязки;
- pending-команды, futures и временные задачи;
- tombstones, относящиеся к этому шлюзу;
- все retained MQTT-топики интеграции для этого шлюза.

Не затрагивайте другие ESP32. Не отправляйте Factory Reset самостоятельно: это ответственность Manager. Не ставьте Factory Reset в очередь, если ESP32 offline.

Manager очищает собственные retained identity/profile/availability/OTA status, общие сущности и запись физического устройства. Потребитель очищает собственные retained-топики.

Обработчик регистрируется при setup и снимается при unload. При unload также отменяются futures/tasks и закрываются MQTT-подписки.

Если cleanup handler выбрасывает исключение, Manager записывает ошибку и продолжает остальные обработчики. Автоматического отката частично выполненной очистки нет. Поэтому handler должен логировать детали и обеспечивать идемпотентность.

## 10. Управление ESP32 и операции

OTA, restart, Factory Reset и полное удаление физического устройства выполняются через ESP32 Manager. Специализированная интеграция не должна публиковать общие системные команды напрямую.

**Ограничение текущего API v1:** API предоставляет snapshots и регистрацию cleanup handlers. Универсального метода выполнения произвольных product operations в нём пока нет. Поле operations в snapshot — метаданные профиля, а не готовый исполнительный API.

До появления согласованного общего API продуктовые команды могут использовать собственный документированный MQTT-контракт специализированной интеграции. Это исключение не распространяется на общие системные команды ESP32.

## 11. UI, сервисы и конфигурация

- Сервисы специализированной интеграции принимают стабильный device_id, а не имя шлюза или индекс строки UI.
- Панель/карточка не публикует MQTT напрямую: она вызывает сервисы интеграции.
- Валидация параметров выполняется на стороне Python до публикации MQTT и повторно на прошивке.
- UI не является источником истины: состояние восстанавливается из Manager API и продуктовых retained snapshots.
- Несохранённые пользовательские изменения в формах не должны затираться фоновыми обновлениями.
- Общие цвета, статусы, подписи и паттерны управления должны быть согласованы между панелями экосистемы.
- Секреты не возвращаются frontend и не сохраняются в браузерном состоянии.

## 12. Минимальный чек-лист новой интеграции

- [ ] В manifest.json объявлена зависимость esp32_ota.
- [ ] Setup проверяет наличие API и поддерживаемую версию.
- [ ] Начальное состояние загружается через get_devices().
- [ ] Подписки на added/updated/removed события зарегистрированы и снимаются при unload.
- [ ] Интеграция не подписывается на общие identity/profile/availability топики.
- [ ] Общая запись ESP32 не создаётся повторно; дочерние устройства используют via_device.
- [ ] Общие метаданные и пользовательское имя не дублируются.
- [ ] Профиль проверяется до активации продуктовой логики.
- [ ] Продуктовые MQTT payload валидируются; retained и QoS документированы.
- [ ] Команды имеют correlation ID/timeout, где требуется ответ.
- [ ] Cleanup handler удаляет все данные интеграции для одного шлюза и не затрагивает остальные.
- [ ] Повторное обнаружение после удаления не восстанавливает старые данные.
- [ ] Проверены перезапуск HA, offline/online, OTA/profile change и несколько ESP32.
- [ ] README описывает установку, зависимости, сущности, сервисы, MQTT и удаление.

## 13. Обязательные сценарии тестирования

1. Установка Manager и специализированной интеграции с нуля.
2. Setup при отсутствующем/неподдерживаемом API — корректный retry, без собственного discovery.
3. Обнаружение ESP32 до установки специализированной интеграции; после установки snapshot получен из Manager.
4. Перезапуск HA и восстановление устройств/сущностей без дубликатов.
5. MQTT disconnect/reconnect и изменение availability.
6. Очистка retained profile перед OTA и появление нового профиля.
7. Несовпадающий/неизвестный профиль и восстановление подходящего профиля.
8. Несколько ESP32 и одинаковые продуктовые child IDs на разных шлюзах.
9. Удаление одного шлюза при online и offline.
10. Очистка entities, child devices, storage, pending tasks и retained-топиков.
11. Повторное обнаружение после удаления: старые имена, Areas, привязки и сущности не должны воскресать.
12. Выгрузка специализированной интеграции и Manager без оставшихся listeners/handlers.

**Главное правило:** ESP32 Manager владеет физическим ESP32 и его общим жизненным циклом. Специализированная интеграция владеет только своим продуктом и обязана полностью убирать собственные данные по запросу Manager.
